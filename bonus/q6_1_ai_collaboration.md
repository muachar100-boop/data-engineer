##### Step 1：数据读取与检查

目标：先搞清楚实际需要处理的评论是什么样的。

你的数据来自 Olist 数据库中的 `order_reviews` 表，重点字段是：

- `review_id`：评论 ID。
- `review_score`：评价分数（1～5）。
- `review_comment_message`：葡萄牙语评论内容。

README 要求处理评分 ≤3 的差评，大约 1～2 万条。但实际数量需要从数据库中统计，不能直接假设。

首先用 SQL 读取数据：

```
SELECT
    review_id,
    review_score,
    review_comment_message
FROM order_reviews
WHERE review_score <= 3;
```

然后使用 pandas 检查：

- 总共有多少条差评？
- 其中多少条评论为空？
- 评论长度如何分布？
- 有多少完全相同的评论？
- 评论中是不是存在 `ruim`、`atrasado` 等重复出现的简单表述？
- 有多少评论包含多个问题？

这里最重要的思考是：并不是每一条差评都需要 LLM。

例如 `ruim` 表示“差”，但没有说明具体原因，你可以通过简单规则识别，而不必为其调用一次大模型。

| 需要掌握的知识             | 推荐工具           |
| ------------------- | -------------- |
| SQL 数据筛选、NULL 处理    | MySQL 8.0      |
| DataFrame、缺失值、重复值统计 | pandas         |
| 字符串处理、文本长度统计        | Python         |
| 文本分布分析              | matplotlib（可选） |

完成标志： 得到一个待处理的差评数据集，同时明确它的数量、内容分布以及主要数据问题。

##### Step 2：设计分流策略（Routing Strategy）

目标：降低成本，把简单评论交给规则，复杂评论交给 LLM。

这是这道题非常关键的决策之一。

可以设计三条处理路径：

输入：一条葡萄牙语差评

路径 A

空评论

不调用 LLM

标记为无文本证据

路径 B

简单、明确的评论

规则/词典识别

直接生成结构化结果

路径 C

复杂、多问题评论

调用 LLM

抽取问题、证据和严重程度

需要注意：不能简单地认为短评论就一定适合规则。比如 `quebrado`（损坏）可以相对明确地映射为质量问题，但 `ruim`（差）只能表达负面情绪，不能擅自分类为质量问题。

你还需要考虑如何处理具有相同文本的评论，避免重复调用模型，同时保留不同的 `review_id`。

| 需要掌握的知识                 | 推荐工具           |
| ----------------------- | -------------- |
| Rule-based NLP（规则式文本处理） | Python         |
| 正则表达式 Regex             | `re`           |
| 文本标准化、去重与缓存             | pandas、hashlib |
| 条件判断与任务路由               | Python         |

完成标志： 明确哪些数据可以直接规则处理，哪些需要 LLM，并统计每条路径占多少数据。

##### Step 3：设计 Prompt 和 JSON 结构

目标：让 LLM 稳定地按照要求输出结果，而不是自由回答。

你需要定义模型的工作规则。例如：

1. 只从原始评论中抽取有证据支持的问题。
2. 问题类别只能使用 README 规定的类别。
3. 同一条评论允许出现多个问题。
4. `evidence_quote` 必须是评论中真实存在的葡萄牙语文本。
5. `evidence_quote_en` 是对应的英文翻译。
6. 无法判断的问题不允许凭空补充。
7. 输出必须符合指定 JSON Schema。

例如对评论：

`O produto chegou atrasado`

应该抽取 `delivery_late`，而不是推测物流公司、商家或商品本身有质量问题。

葡萄牙语处理也是这个阶段的重点。你可以比较两种方法：先翻译成英语再提取，或者直接让多语言 LLM 从葡萄牙语原文提取并翻译证据。后一种通常更简洁，但需要验证实际质量。

| 需要掌握的知识            | 推荐工具             |
| ------------------ | ---------------- |
| Prompt Engineering | LLM              |
| JSON、JSON Schema   | Python `json`    |
| Structured Outputs | 支持结构化输出的 LLM API |
| 数据结构与字段验证          | Pydantic         |
| 多语言 NLP 与证据约束      | LLM、人工检查         |

完成标志： 写好 `prompt_template.txt`，并在少量真实评论上验证模型输出符合规定。

##### Step 4：实现批量抽取 Pipeline

目标：把前面的分流策略和 Prompt 变成真正可执行的 Python 程序。

你要完成 `extract_reviews.py`，实现类似下面的逻辑：

```
for review in reviews:    if is_empty(review):        result = handle_empty(review)    elif is_simple(review):        result = rule_based_extract(review)    else:        result = llm_extract(review)    validate(result)    save(result)
```

实际实现还要增加：

- API 调用异常处理与重试。
- 批量请求和并发限制。
- 结果缓存，防止重复付费。
- 每次请求的 token 和费用记录。
- 断点续跑，避免执行中断后重新处理全部数据。

你需要比较单条请求和批量处理的成本及耗时。这里的批量可能指多条评论合并到一次请求，也可能指使用 API 提供的 Batch 服务，两者需要分别评估，不能默认哪种更便宜。

| 需要掌握的知识                | 推荐工具             |
| ---------------------- | ---------------- |
| Python 函数与 Pipeline 设计 | Python           |
| API、HTTP、JSON 请求       | LLM API SDK      |
| Batch Processing       | API Batch / 并发处理 |
| 异常处理与重试                | `try/except`     |
| 数据持久化与日志               | JSON、logging     |

完成标志： 程序能够对选定差评自动抽取，最后生成 `extracted_issues.json`。

##### Step 5：验证结构化输出

目标：保证结果不仅能生成，而且能被程序正确使用。

需要检查：

- 每条记录是否包含全部要求的字段。
- `category` 是否属于允许的类别。
- `severity` 是否为 `low`、`medium` 或 `high`。
- `sentiment_score` 是否在 -1 到 1 之间。
- `confidence` 是否在 0 到 1 之间。
- `evidence_quote` 是否真的来自原文。
- 是否存在同一个问题被重复抽取的情况。

特别注意：合法 JSON 不代表内容正确。

例如模型输出的 category 格式完全正确，但把送货延迟误判为商品损坏，仍然属于抽取错误。

需要掌握 JSON Schema、Pydantic 数据验证、异常处理和基本的数据质量检查。

完成标志： 所有输出都通过结构验证，无法通过的记录被修复、重试或明确记录为失败，而不是悄悄丢弃。

##### Step 6：成本分析与准确率评估

这一阶段有两个独立任务。

任务 A：成本分析

README 给出的限制是：

总预算上限

# $3 USD

时长限制

# 40 分钟

你需要记录输入 token、输出 token、成功处理条数、总费用和单条平均费用，并分析是否能够在限制内完成。

成本公式：

\\[ C=\frac{T\_{in}}{10^6}P\_{in}+ \frac{T\_{out}}{10^6}P\_{out} \\]

其中：

- \\(T\_{in}\\)：输入 token 数量
- \\(T\_{out}\\)：输出 token 数量
- \\(P\_{in},P\_{out}\\)：所选模型每百万 token 的实际计费价格

不能只根据请求次数估算费用，因为不同评论长度和生成结果长度不同。

需要掌握 Token、API Pricing、Batch、缓存机制以及简单的成本统计。

任务 B：准确率评估

题目特别提出：你没有现成的 Ground Truth（标准答案），如何知道模型提取正确？

一个合理的方法是：

1. 从处理结果中抽取 30 条评论，覆盖规则路径、LLM 路径及不同问题类型。
2. 不看模型结果，人工阅读原始葡萄牙语评论（必要时借助翻译），独立标注问题。
3. 将人工标注与 Pipeline 输出进行对比。
4. 计算 Precision、Recall 和 F1，并分析错误案例。

例如：

|      | 人工标注                         | Pipeline 提取    |
| ---- | ---------------------------- | -------------- |
| 评论 A | delivery_late                | delivery_late  |
| 评论 B | quality_defect               | quality_defect |
| 评论 C | wrong_product                | missing_item   |
| 评论 D | delivery_late、quality_defect | delivery_late  |

A、B 正确；C 分类错误；D 只找到其中一个问题。

因此除了整体准确情况，还应该关注多问题评论的漏检。

注意：只有 30 条人工样本，评估结果只能作为初步质量估计，不能证明所有 1～2 万条评论都有相同准确率。

| 需要掌握的知识                   | 推荐工具             |
| ------------------------- | ---------------- |
| Ground Truth 与人工标注        | Excel / CSV      |
| Precision、Recall、F1       | scikit-learn     |
| 错误类型分析                    | pandas           |
| Stratified Sampling（分层抽样） | pandas           |
| Token 与 Cost 统计           | API Usage、Python |

完成标志： 有真实成本数据、30 条人工验证样本，以及可解释的准确率结果。

请统计不同处理路径的记录数量及占比，分析分流规则可能出现的误判和漏判，并结合 $3 总预算及 40 分钟限制，评估后续批量抽取的可行性。

本轮只完成数据检查、分流策略分析和初步报告，暂时不要进行付费 API 调用，不修改前面模块的已有结果。将新增内容保存在 q4_llm_extraction/ 目录下，并简单说明分析结果和下一步应该如何设计 Prompt。

这样推进的好处是，你可以先看到真实的数据特征，再决定后面 LLM 的 Prompt、批量方式和成本控制方法，而不是直接搭建一条可能花费超预算、准确率又难以验证的 Pipeline。

## 4. AI 的最终答案有什么错误或不足？

> 你是怎么发现并修正的？

### 4.1 第一轮 ChatGPT 框架的盲区

我沿用了这个框架，所以它的盲区后来一个个都变成了实际问题：

| 盲区 | 后来怎么暴露 | 我的修正 |
|---|---|---|
| **成本被放在第 6 步，当作事后报告**，而不是从头到尾的硬约束 | Codex 每轮都在提升质量，v6 全量估算 $3.97，超出预算 | 运行前读取开发账本，剩余预算 = $3 − 已花费；每个请求先按最坏情况预留费用，超出就停发；37 分钟后停发新请求 |
| **没有提到情绪和严重度需要先定义量表** | 成了最大的时间黑洞：v6 → v7 → v8 反复改量表 | 冲突规则 R1–R6 由我逐条裁决；定成 5 档后不再修改 |
| **“抽 30 条人工标注，计算 P / R / F1”**，没有区分开发集和验证集 | 开发集 30/30 全部通过，是假信号 | 先封存标签并记录哈希，先登记判定规则，同一批样本上放对照组，每次换新样本 |
| 建议使用 Batch 服务，**没有指出 24 小时完成窗口和 40 分钟时限冲突** | Codex 核对 README 后才指出 | 改用同步请求 + 8 线程并发 |
| 暗示规则能挡住大量短差评 | 实测 “ruim” 完全匹配只有 8 行。规则省下的主要是 8,132 行空文本；10 条候选规则只能多覆盖不到 1% | 规则只做整字段完全匹配，不再扩大 |
| 给得过于细节：7 步 × 知识表 × 工具表，却没有优先级 | 信息很多，真正关键的约束反而被淹没 | 只采用了推进顺序 |

### 4.2 Codex 最终答案（v6）的问题

1. **把 $3 预算当软约束。** 全量估算 $3.97（含余量 $4.88），而且每一轮迭代都在优化质量，没有一轮在压成本。
   - **怎么发现**：我拿它每轮给出的估算对照 README 的预算，发现迭代越多越超支。
   - **怎么修正**：转用 Claude，先冻结基线，再在独立样本上对比更便宜的模型。
2. **开发集被 Prompt“泄漏”。** v6 Prompt 里多处写着“约 -0.5”，这个锚点来自开发集（30 条标签中有 13 条是 -0.5）。两个模型的情绪分数都集中在 -0.5，开发集却 30/30 全部通过，看起来很完美。
   - **怎么发现**：对比 4o-mini 时，20 条里有 13 条打成 -0.5，Claude 追查到 Prompt 中的锚点。
   - **怎么修正**：重新设计量表，并且只在新样本上评估。

### 4.3 Claude 最终答案（v8 Prompt + 4o-mini + 4.1-mini 兜底）的问题

1. **质量仍然偏低。** 在 X 批 30 条独立样本上，四字段同时一致只有 13/30（43%），对照组是 17/30，**没有通过事先登记的非劣效门槛**（不低于对照 − 2）。W、X 两批 60 条合计 38%（95% 区间 27–51%），对照为 48%。错误主要集中在类别上：
   - 多标 seller_communication（全量 2,315 条，很可能偏高）；
   - 把主观的“质量不如描述”判成 quality_defect；
   - 多问题评论漏标类别；
   - 情绪偏重：普通投诉打成 -1。

   **怎么发现**：靠“先封存标签 + 先登记规则 + 同批对照”，而不是看绝对分数。如果只看开发集，它会显得没有问题。

   **修正了多少**：
   - **已解决**：编造证据。程序逐条校验引句是否为原文中连续的一段；不合格的单条交给 4.1-mini 重抽，仍失败则记入死信。全量 22,475 条全部通过校验，死信 18 条。
   - **没有解决**：类别判断错误。这一层我没能在预算内修好，只能在报告中写明这是 $3 预算下的取舍，不是验证通过；并提醒 seller_communication 等类别的统计要打折使用。
2. **标签独立性不足。** W、X 两批的 60 条标签由 Claude 预填，我确认时没有改动，所以实质上是 AI 的判断。情绪按 v8 量表标注，天然偏向候选组；即便如此，候选组也只和对照组持平。这一点已写进 `accuracy_evaluation.md` 的局限。
3. **在用过的样本上出现“假改善”。** v7 在已用过的样本上情绪一致从 8/20 提到 14/20，看起来明显进步；换到新样本上只有 13/30，对照组是 19/30。

### 值得记录的 Prompt 工程经验

1. **硬约束写在 Prompt 第一句，并写成“违反就停”。** 否则 AI 默认追求质量，把预算当作参考。
2. **检查 Prompt 里的每个数值锚点是不是来自开发集标签。** 一旦泄漏，开发集指标就完全失去信号。
3. **改善只在新样本上算数。** 先封存标签、先登记门槛，并在同一批样本上放对照组；结果不满意也不事后改门槛。
4. **要求 AI 标明每个数字的来源**：是实测、估计还是假设。
5. **程序能校验的，不交给模型自觉**（例如引句是否是原文中的连续片段）。**程序校验不了的**（类别、情绪），必须人工抽查，而且要盲标。
6. **让 AI 拆解任务时，要同时给出约束和现状**，否则得到的是一份通用教程。

## 5. 如果让你再做一次同样的题，你的第一个 prompt 会怎么写？

```
我要完成 README 中的 Q4.1（Olist 葡语差评结构化抽取），前面模块已完成，MySQL 中已有 order_reviews 表。

【硬约束，任何一步违反都先停下来问我】
1. 总预算 $3，包含开发、调 Prompt、验证和全量运行的全部 API 费用；全量必须在 40 分钟内跑完；不能全部用大模型。
2. 本轮付费调用上限 $0.05。每个数字都标明是实测、估计还是假设。

【我已经定好、你不要改的】
- 情绪（5 档）和严重度（3 档）的定义与边界样例见 q4_llm_extraction/scale.md。
- 评估协议：我会先人工盲标 60 条独立样本，封存后记录哈希；判定门槛在运行前登记，之后不改。这 60 条不能用来调 Prompt，Prompt 中也不能出现来自任何标签的数值锚点。

【本轮只做三件事】
1. 数据检查：评分 ≤3 的行数、空文本、整字段重复、长度分布；按“空文本 / 整字段完全匹配的规则 / LLM”统计分流比例，说明每条规则可能误判的例子。
2. 成本实测：在 2–3 个候选模型上，每个模型用 20 条开发样本，测每批 1 / 5 / 10 条时的每条输入、输出 token、缓存命中和耗时，再推算全量费用和墙钟时间，判断哪些组合能在预算和时限内完成。
3. 列出 README 中所有会影响成本或评估、但没有定义清楚的地方，等我裁决。

先不要写完整 Pipeline，也不要优化 Prompt 质量。结果写到 q4_llm_extraction/phase0_report.md，最后告诉我下一步需要我做哪些决定。
```

和第一次相比，变化有三点：
- 预算和时限从第一句起就是硬约束；
- 量表和评估协议由我先定好、封存，AI 不能改；
- 先实测成本、选定模型，再调 Prompt。

第一次的顺序是先在 4.1-mini 上把质量调好，再发现付不起；而质量和成本两头的结论，都只有在新样本上才可信。
